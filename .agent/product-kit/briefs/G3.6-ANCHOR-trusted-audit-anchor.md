# G3.6-ANCHOR — Trusted audit-chain head

## Decision needed

Choose an already-approved WORM provider/account and a retention policy for an independent, content-free checkpoint of each audit-chain head. The audit ledger is retained indefinitely, so finite checkpoint retention would weaken tail-truncation detection after expiry. Also authorize the scoped runtime credential, any provider dependency or transport, and recurring cost before implementation.

## Evidence

- Independent verification found that deleting the newest valid audit rows leaves a valid hash-chain prefix; no trusted latest head is stored outside the ledger.
- The repository has no configured WORM account or trusted checkpoint service. ADR 0012 compares Amazon S3 Object Lock, Azure Blob immutable storage, and Google Cloud Storage Bucket Lock. See `docs/adr/0012-audit-chain-head-anchor.md` in the G3.6 worktree.
- The G3.6 handoff also records unresolved fail-closed behavior for spend-cap writes and audit-history reads, and missing live Prisma/provider verification.

## Recommendation

Keep G3.6 blocked until the founder selects an existing provider/account and retention, and explicitly authorizes the required credential scope, dependency or transport, and cost. Do not silently weaken the tamper-evidence bar or create an account.

## Choices

1. Authorize Amazon S3 Object Lock using an existing account and name the retention/hold policy.
2. Authorize Azure Blob immutable storage using an existing account and name the retention/hold policy.
3. Authorize Google Cloud Storage Bucket Lock using an existing account and name the retention policy.
4. Name another already-approved WORM service and its account/retention, or keep G3.6 blocked while making no provider choice.

No provider, account, retention setting, credentials, dependency, infrastructure, or spend is authorized by this brief.
