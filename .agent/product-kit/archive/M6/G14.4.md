# G14.4: Vetting and install pipeline for third-party tools, skills and MCP servers: provenance, permission review, sandbox, pin; no runtime self-install

Exit evidence required: Installing without founder confirmation is impossible; each item has a review record; community skills are treated as untrusted because malicious ones have been reported.

## Delegation decision
Alone or helpers: helpers
Why: Helper subagent (kit-reviewer) performs an independent adversarial review of security gates, zero-runtime self-install invariants, and untrusted community quarantine before landing.
Roles: reviewer
Host can start sub-agents: yes
Helpers not started because: Reviewer is invoked via Antigravity native subagent infrastructure (kit-reviewer).

## Plan
1. Define third-party capability provenance and vetting types in `src/types/vetting.ts` (`CapabilityProvenanceSchema`, `SecurityFindingSchema`, `CapabilityRiskAssessmentSchema`, `CapabilityVettingProposalSchema`, `CapabilityVettingRecordSchema`).
2. Enforce zero runtime self-install: agents cannot self-install; any proposal halts in `pending_founder_confirmation`.
3. Implement `CapabilityVettingPipeline` in `src/lib/server/capabilities/vetting-pipeline.ts`:
   - Enforce provenance verification and strict semver pinning.
   - Enforce permission review (wildcard disallowance, forbid skill permissions).
   - Enforce static content inspection against malicious patterns (prompt injection, dynamic code eval, remote shell pipes).
   - Default all community candidates to quarantined untrusted tier.
   - Enforce that installation is physically impossible without cryptographic Founder confirmation with `payloadHash` binding.
   - Produce permanent, tamper-evident vetting records.
4. Integrate with `CapabilityRegistry`, `SkillReviewStore`, and `InMemoryAuditStore`.
5. Author comprehensive automated tests in `tests/capabilities/g14_4_vetting_and_install_pipeline.test.ts`.
6. Verify typecheck, lint, build, and test suite.

## What changed
- `src/types/vetting.ts`: Codified `CapabilityProvenanceSchema`, `SecurityFindingSchema`, `CapabilityRiskAssessmentSchema`, `CapabilityVettingProposalSchema`, `CapabilityVettingRecordSchema`, and domain errors (`RuntimeSelfInstallForbiddenError`, `FounderConfirmationRequiredError`, `UnpinnedVersionForbiddenError`, `SecurityVettingFailedError`, `UntrustedQuarantinedError`).
- `src/lib/server/capabilities/vetting-pipeline.ts`: Implemented `CapabilityVettingPipeline` with `vetCandidate`, `proposeInstall`, `confirmInstall`, and `attemptRuntimeSelfInstall`.
- `tests/capabilities/g14_4_vetting_and_install_pipeline.test.ts`: 13 automated tests verifying zero self-install, founder confirmation enforcement, durable review records, detection of prompt injection and malicious shell pipes, version pinning, wildcard permission rejections, and `CapabilityGateway` quarantine integration.

## Why
Per `AGENTS.md` and Milestone M6, LLMs and agents must never have authority to alter security boundaries, install packages, or introduce ambient capabilities without cryptographic founder confirmation. Community skills have known attack vectors (prompt injection, permission escalation, data exfiltration), making mandatory provenance, permission vetting, untrusted defaulting, and founder confirmation non-negotiable.
