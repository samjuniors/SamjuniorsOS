# Finding G11.2: SQLite Test Isolation and Windows Schema Engine Failures

- Severity: medium
- Date: 2026-10-26
- Gate: G11.2 integration verification

## Work completed so far

- Runtime SQLite paths now resolve from the Prisma schema directory. Prisma CLI operations keep schema-relative URLs instead of receiving an absolute Windows file URL.
- The test runner uses a disposable database copy from `prisma/db/custom.db`, gives staging/deploy checks separate scratch databases and free local ports, and runs durable-store tests against a copied `.data` directory.
- Migration-related suites now build their temporary SQLite URLs relative to `prisma/schema.prisma` and keep their databases inside the runner's scratch directory.
- Test cleanup is limited to the disposable copy; tests that change their working directory continue using their own temporary data roots.
- Focused staging reachability, data-directory isolation, and selected decision-suite checks passed.

## Remaining blocker

- Full `npm test` runs on Windows with Node.js 24.20.0 and Prisma 6.11.1 repeatedly fail in migration-focused suites with an empty `Schema engine error:`. The affected suites include backup/restore, multi-instance concurrency, store migration parity, versioned migrations, M2 knowledge persistence, and M5.3 authoritative read model.
- New isolated diagnostics: `npx prisma -v`, `npx prisma validate`, and `npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` pass. A scratch `prisma db push` fails with a blank schema-engine error for absolute Windows file URLs (`file:C:/...` and `file:///E:/...`) but passes with `file:./db/...`.
- After changing the runner and affected suites to schema-relative scratch URLs, `staging_reachability` passes, but the focused `versioned_migrations` suite still fails at `npx prisma migrate deploy` with a blank schema-engine error, despite its relative URL. The remaining migration-engine cause is **NOT VERIFIED**.
- Kit protocol §5 requires stopping after repeated failures of the same check. Do not run `kit sync` or land G11.2 until the schema-engine failure has an independent, reviewable resolution and the configured full check passes.

## Attempt log

- First full-run attempt: 80 suites passed, 20 were skipped, and 6 failed with the blank schema-engine error listed above.
- Second full-run attempt: the then-current runner produced `.data` missing/orphan-marker failures. This exposed that the harness could write to the repository's durable data directory; the first-run side effects are documented below.
- Third full-run attempt, after adding scratch database and copied-data isolation: the same schema-engine failures recurred in backup/restore and later migration-focused suites. The run was stopped rather than repeated again under protocol §5.
- Earlier focused runs of the six affected suites passed individually, but that did not clear the configured integration check. After the URL-path edits, `staging_reachability` passed and `versioned_migrations` failed again at `prisma migrate deploy`.
- Focused deploy, durable-data isolation, and selected decision suites also passed in earlier runs.
- Latest `npm run typecheck`, `npm run lint`, `npm run build`, `git diff --check`, `node --check scripts/test-runner.mjs`, and `node .agent/product-kit/kit.mjs layout check` all PASS. The build reports a mixed static/dynamic `runtime.ts` import warning and a chunk over 500 kB.

## Operator note

- The first full test run used the old runner cleanup and test files that wrote directly to repository `.data`. Several durable files changed. No pre-run backup was available, so their current contents were left intact rather than guessed at or deleted. The updated runner isolates future test writes; that change does not restore the earlier contents.
