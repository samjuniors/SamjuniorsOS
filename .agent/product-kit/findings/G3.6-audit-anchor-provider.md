# G3.6 blocker: trusted audit-head anchor provider and retention

**Severity:** High — blocks the G3.6 tamper-evidence exit evidence.

## Evidence

- Independent verification of `ec0991ccf2080d9a654d2646bc30e2edadfd7ff6` found that removing the newest valid audit rows leaves a valid hash-chain prefix. No trusted latest head exists outside the primary ledger.
- Repository inspection found existing Prisma and file audit stores, but no configured WORM object-storage provider/account or trusted checkpoint service.
- The proposed provider-neutral design is documented in `docs/adr/0012-audit-chain-head-anchor.md`; AWS S3 Object Lock, Azure Blob immutable storage, and Google Cloud Storage Bucket Lock are compared there using official vendor documentation.
- G3.6's existing audit retention is indefinite. A finite object-lock retention period would only establish truncation detection while the checkpoint remains protected.
- G3.6 handoff records the additional spend-cap audit failure path: mutation persists before audit and the logger swallows failures; history reads also hide chain errors by returning an empty array.

## Proposed resolution

Select an already-approved WORM storage provider and account; approve a retention policy matching the audit-retention requirement, the narrowly scoped writer identity, credentials, required SDK or transport, and recurring cost. Then implement per-append head checkpoints and fail-closed recovery, make spend-cap changes report and safely handle audit failures, and verify against a live configured database and the selected provider.

## Constraints

- No provider account, credential, SDK, schema migration, infrastructure, or spend was created or changed.
- The user approved retaining the full tamper-evidence bar and designing an anchor (`use recomendation`); the user has not selected a provider or retention duration.
- Do not claim complete tail-truncation detection, mark G3.6 done, or land G3.6 until the proposed anchor is implemented and independently verified.
