# Finding G2.7: Owner-Scoping Gaps in Flat Storage and Secondary Stores

**Severity:** Low (Deferred by design for single-operator v1; relevant only when scaling past single human)  
**Gate:** G2.7 (Platform Scale-Later Seams)  
**Date:** 2026-10-21  

---

## 1. Summary

During the Gate G2.7 audit of all 23 Prisma models and 16 server stores, the core Personal Mind stores (`SophiaMemoryStore` and `ConversationStore`) were confirmed to be cleanly owner-scoped by `founderId`. However, three secondary stores currently utilize unpartitioned flat maps or query patterns that do not isolate data by owner:

1. **`CommunicationStore` (`src/lib/server/communication/store.ts`):** Contacts, drafts, and communication messages are persisted in `.data/communication_contacts.json`, `communication_messages.json`, and `communication_drafts.json` without an explicit `founderId` or `ownerId` property.
2. **`WorkflowStore` (`src/lib/server/workflow/store.ts`):** Workflow instances are stored in `.data/workflow_instances.json`. While instances record `userId` when initiated through Prisma, the flat JSON persistence layer has no partition key.
3. **`ApprovalStore.list()` (`src/lib/server/authorization/approval-store.ts`):** Approval list queries accept workflow, step, and classification filters, but do not support an owner or tenant filter.

---

## 2. Evidence

- `src/lib/server/communication/store.ts` (lines 14–45):
  ```typescript
  export interface Contact {
    id: string;
    name: string;
    email: string;
    // Missing ownerId / companyId field
  }
  ```
- `src/lib/server/workflow/store.ts` (lines 40–80):
  ```typescript
  // Flat map keyed by workflowInstanceId without owner isolation
  private instances: Map<string, WorkflowInstance> = new Map();
  ```
- `src/lib/server/authorization/approval-store.ts` (lines 129–137):
  ```typescript
  public async list(filter?: ApprovalFilter): Promise<FounderApprovalRecord[]> {
    // filter has no userId / ownerId field
  }
  ```

---

## 3. Impact Assessment

- **Single-Founder V1 (Current):** **Zero impact.** SamJuniorsOS operates exclusively for one founder. All workflows, contacts, and approvals belong to this single operator.
- **Multi-Operator Scaling (Future - Gate G10 / Phase 2.3C):** If a second human joins the system without addressing these gaps, contacts and workflow instances would be visible across operators.

---

## 4. Proposed Resolution / Future Step

When the founder decides to authorize multi-user operation (Gate G10):
1. Add `ownerId: string` to `Contact`, `CommunicationDraft`, and `CommunicationMessage` models.
2. Extend `ApprovalFilter` with `ownerId?: string`.
3. Migrate from `.data/*.json` flat files to the PostgreSQL schema (Phase 2.3C) with Row-Level Security (RLS) or tenant-keyed tables.
4. **No action required in v1.** Building multi-operator fixes now would violate the single-founder invariant.
